# 用 Mac 记录 RK3588 出厂启动日志

任务卡 #1 · 正点原子 ATK-DLRK3588B · 每一步说明用途与验收 · 2026 年 10 月 3 日

本教程按 Claude 计划的第一张任务卡展开：通过底板调试串口进入出厂系统，保存完整启动日志，并取得 uname -a 与 /etc/os-release 的输出。文件夹里的系统镜像和烧录工具留到后续烧录阶段使用。

**本卡边界：**不烧录、不升级、不修改板上系统设置。Mac 端准备 picocom 和日志目录；板上仅观察启动、登录和执行两条只读查询。每一步出现错误都先保留完整输出，停在当前步骤。

## 先理解连接和记录顺序

Mac 通过 USB 数据线连接底板上标有 **UART / 调试串口** 的 Type-C 口。板载 CH343G 把 USB 通信转换成 RK3588 的调试串口。另两个 USB 3.1 Type-C 口不用于本次调试连接。[1][2]

厂商硬件参考手册 §3.16 明确：CH343G 由调试 USB 独立供电，不受板子的电源开关控制；这个调试口不能代替板子的 12 V 电源。因此可以先让 Mac 识别串口、开始记录，再给主板上电。[2]

**按这个顺序做：**主板保持未上电 → 接调试 USB → 找到串口设备 → 配置并打开 picocom 和日志 → 看到 Terminal ready → 接通主板 12 V 电源 → 等待启动与登录 → 执行只读查询 → 退出串口、检查日志。

开始条件是主板尚未运行、调试 USB 尚未接入。若板子已经在运行，先说明当前状态，确认后再安排完整启动记录，不直接拔电重来。

| 操作发生在哪里 | 输入什么 |
| --- | --- |
| Mac 普通终端 | uname -m、安装 picocom、查看 /dev、启动日志、检查文件 |
| picocom 中已登录的板子 shell | uname -a、cat /etc/os-release |
| 另开的 Mac 终端 | 检查日志文件是否已创建和增长 |

**最容易混淆的地方：**同样是一个终端窗口，启动 picocom 后，输入的普通字符会送给板子。要记录板子的系统信息，必须等板子登录成功；在 Mac shell 执行 uname -a 得到的是 Mac 信息。

## 本卡最终要交回什么

完整原始启动日志；Mac 会话记录；板子 uname -a 与 cat /etc/os-release 的输出；Mac 架构、串口设备名、波特率和 picocom 版本。截图只作为画面补充，不能代替全文日志。

## 第 1 步：确认 Mac 架构和串口工具

**在做什么、为什么：**确认当前终端运行的架构，并检查串口工具。架构会影响软件或驱动的兼容性，先记录再判断。

下面查看 Mac 当前环境的架构：

```bash
uname -m
```

arm64 表示 Apple 芯片原生环境。x86_64 可能是 Intel Mac，也可能是 Rosetta 环境，不能只凭这一行断言芯片型号。把实际输出带回来。

下面检查 picocom 是否已可用，并查看它支持的选项：

```bash
picocom --help
```

若能显示帮助，不重复安装。若提示 command not found，且你已确认 Homebrew 可用，则下面在 Mac 安装 picocom，并关闭本次 Homebrew 自动更新：[3]

```bash
HOMEBREW_NO_AUTO_UPDATE=1 brew install picocom
```

安装成功后重新执行 picocom --help。**成功现象：**帮助中有版本信息、--logfile，以及本构建的自定义波特率支持信息。当前 Homebrew 发行版 2024-07 的 Mac 源码支持自定义速率，但最终还需实际驱动和硬件配合。[3][4]

**证据：**uname -m 的实际输出、picocom 帮助。若安装失败或缺少日志选项，保存输出并停下。这里不安装来源未核实的串口驱动，也不调整 Mac 安全设置。

## 第 2 步：建立本次独立的证据目录

**在做什么、为什么：**让启动原始字节与 Mac 会话分别保存，并使用时间戳防止不同启动记录混在一起。

下面在 Mac 创建目录和文件路径。双引号保护目录名中的空格：

```bash
RK_EVIDENCE="$HOME/Documents/RK3588 Microduck/task1/evidence"
mkdir -p "$RK_EVIDENCE"
RK_RUN="$(date +%Y%m%d-%H%M%S)"
RK_BOOT_LOG="$RK_EVIDENCE/boot-$RK_RUN.txt"
RK_SESSION_LOG="$RK_EVIDENCE/session-$RK_RUN.txt"
```

下面记录当前 Mac 环境及工具选项：

```bash
uname -m > "$RK_EVIDENCE/mac-arch-$RK_RUN.txt"
picocom --help > "$RK_EVIDENCE/picocom-help-$RK_RUN.txt" 2>&1
```

**成功现象：**目录可创建，帮助与架构文本可查看。变量只在当前终端会话有效。重新采集时生成新的 RK_RUN 和两条日志路径，保留旧记录；不要覆盖已有证据。

## 第 3 步：比较插线前后的串口设备

**在做什么、为什么：**识别本次新接入的调试口，避免把蓝牙或别的 USB 串口当作开发板。主板 12 V 电源此时保持未接通。

先在 Mac 默认的 zsh 终端记录插线前的设备列表：

```bash
printf '%s\n' /dev/tty.*(N) /dev/cu.*(N) \
  | sort | tee "$RK_EVIDENCE/ports-before-$RK_RUN.txt"
```

这与查看 ls /dev/tty.* 的目的相同，同时列出 cu 入口。zsh 的 (N) 表示没有匹配设备时忽略该模式；sort 排序便于比较，tee 同时显示和保存结果。

现在把 Type-C 数据线接到底板 UART / 调试串口，另一端接 Mac。只接调试 USB，主板仍保持未上电。线必须支持数据传输。

随后执行同样的枚举，保存插线后的结果：

```bash
printf '%s\n' /dev/tty.*(N) /dev/cu.*(N) \
  | sort | tee "$RK_EVIDENCE/ports-after-$RK_RUN.txt"
```

**成功现象：**出现新串口节点，通常有相同后缀的 /dev/tty.* 与 /dev/cu.*。本次由 Mac 主动连接，选对应的实际 /dev/cu.* 入口。不要猜 usbserial、usbmodem 或数字后缀。

若没有新增节点，就停在这里，带回前后两份列表以及接线照片；保持主板未上电。具备独立 USB 供电条件，不等于每台 Mac 都会自动识别成功。

## 第 4 步：确认速率，并填写实际设备名

**在做什么、为什么：**通信两端必须使用一致的速率和帧格式。串口窗口能打开，不代表参数已经正确。

可访问的官方快速体验手册 §1.2 明确出厂默认波特率为 **1500000（1.5 M）**。本次未读到语雀新版《调试串口配置手册》正文；若你当前手册给出不同值，先停下核对，不能把经验值覆盖手册。[5]

下面设置已核对的默认速率，并把示例设备名替换为你刚才实际新增的 cu 节点：

```bash
RK_BAUD=1500000
RK_PORT='/dev/cu.替换为实际新增设备'
```

本教程显式设置 8 数据位、无校验、1 停止位，即 8N1，并关闭流控。波特率已由上述官方页面确认；已访问资料未逐项写出其他参数，需以对应手册和实际可读输出核对。

**证据：**前后设备列表、实际 RK_PORT、手册名称与速率。现在仍不要给主板上电。

## 第 5 步：先打开串口，同时开始两份日志

**在做什么、为什么：**picocom 的 --logfile 保存收到的原始字节；Mac 自带 script 另保存终端会话，包括 picocom 的参数摘要和错误。这样即使串口打开失败，也有完整文字可排查。[4][6]

下面在 Mac 的同一个终端执行。变量必须来自前面步骤，设备名已经替换，主板仍未上电：

```bash
script -q -F "$RK_SESSION_LOG" \
  picocom --baud "$RK_BAUD" \
  --flow n --parity n --databits 8 --stopbits 1 \
  --logfile "$RK_BOOT_LOG" "$RK_PORT"
```

| 命令部分 | 在做什么 |
| --- | --- |
| script -q -F 会话文件 | 录下 Mac 终端显示的内容；-F 每次写入后刷新输出缓冲 |
| --baud / --flow n | 指定波特率，并关闭流控 |
| --parity n / --databits 8 / --stopbits 1 | 设置 8N1 帧格式 |
| --logfile 原始日志 | 保存串口收到的数据，已有文件会追加 |
| 实际 /dev/cu.* | 打开你刚才确认的调试设备 |

**成功现象：**参数摘要显示所选设备、1500000、8N1、无流控，最后出现 **Terminal ready**，且没有配置错误或 Settings mismatch。picocom 源码在提示 ready 前已打开原始日志文件。[4]

现在窗口处于串口会话，不再是普通 Mac shell。先不要向板子输入任何字符。

### 上电前再确认记录确实已开始

另开一个 Mac 终端，用下面命令查看最近的证据文件：

```bash
ls -lt "$HOME/Documents/RK3588 Microduck/task1/evidence"
```

应能看到本次 boot-时间戳.txt 与 session-时间戳.txt。主板未上电时，boot 原始日志为空是正常现象。再打开本次时间戳对应的 session 文本，确认其中包含 picocom 参数和 Terminal ready；确认后保留两个窗口。

**只有 Terminal ready 和日志文件都确认后，才进入下一步上电。**若报错，保持主板未上电，带回 session 文件和终端完整输出。不要直接换成 115200 或通过烧录来解决。

日志命令不加 picocom --echo，也不加 script -k；保持默认不记录本地隐藏输入，避免把登录密码额外写进日志。[4][6]

## 第 6 步：给主板上电，完整观察启动

**在做什么、为什么：**串口已经等待并记录，现在启动 RK3588，才能捕获最早能够输出的串口信息。

按配套电源与板子说明接入 12 V，并打开底板电源开关。调试 USB 保持连接，picocom 持续运行。不要把调试 Type-C 当作主板电源，不使用另两个 USB 3.1 口代替调试口。[1][2]

启动过程中先只观察。不要在 U-Boot 倒计时期间按键，以免打断正常启动。终端可能依次显示早期初始化、U-Boot、内核启动及用户空间信息；具体标记由固件决定。

**成功现象：**启动文字清晰可读，最终出现登录提示或板子的 shell 提示符。若出现乱码，先保存日志并停下核对速率和参数；不要用修改系统波特率的方式绕过。

## 第 7 步：登录并查询出厂系统

**在做什么、为什么：**确认串口不只是能看到输出，还能进入系统执行命令。下面两条查询分别识别当前内核与发行版，不修改配置。

官方快速体验手册对应的出厂 Buildroot 默认 root 自动登录。若已经看到 shell，直接继续；若明确出现该出厂系统的 login 提示，文档给出的用户名和密码均为 root。若提示与资料不一致或登录失败，保存输出并停下，不重置密码。[7]

确认处于板子 shell 后，输入下面命令并回车，查看板子的内核、主机和架构信息：

```bash
uname -a
```

得到完整输出后，再输入下面命令读取发行版标识：

```bash
cat /etc/os-release
```

**成功现象：**uname -a 有可读结果，命令完成后返回板子提示符；同时取得 os-release 的内容。内核或发行版以实际输出为准，不把旧手册里的版本写成实测结果。若文件不存在，保留原始错误，不创建或修改它。

**证据：**两条命令及输出已随串口接收数据进入 boot 日志。可以补一张含 shell 和输出的截图，但仍交回全文文本。

## 第 8 步：正常结束记录

**在做什么、为什么：**关闭 Mac 的串口会话，让程序正常结束并关闭日志文件。

等待最后一个命令输出结束后，在 picocom 窗口按 **Ctrl-A，松开，再按 Ctrl-X**。不是 Command 键，也不是同时按三个键。picocom 退出后，外层 script 随之结束，窗口回到 Mac 提示符。[4]

退出串口不会关闭板子。此时先保持板子当前运行状态，完成证据核对；后续关机按确认后的步骤操作。

## 第 9 步：检查并整理证据

**在做什么、为什么：**验证保存的是从上电前就开始记录的完整原始日志，而不只是末尾几行或一张截图。

回到原来的 Mac 终端，下面查看两份日志的大小：

```bash
wc -c "$RK_BOOT_LOG" "$RK_SESSION_LOG"
```

下面查看原始日志的开头，检查是否包含此次启动的早期内容：

```bash
head -n 60 "$RK_BOOT_LOG"
```

下面查看末尾，确认登录、uname -a 和 os-release 输出被保存：

```bash
tail -n 80 "$RK_BOOT_LOG"
```

**成功现象：**日志非空，开头是本次启动的早期串口输出，末尾包含系统查询。不同固件不一定打印完全相同的 DDR、U-Boot 字样，不能只靠缺少某一个关键词断言丢失；“日志在上电前打开”的操作顺序是关键证据。

用 Mac 文本编辑器从日志中复制两条查询的完整命令与输出，分别保存为 uname-a-时间戳.txt 和 os-release-时间戳.txt。只整理副本，保留 boot 原始文件。原始日志可能含回车或终端控制字符，不要为了美观覆盖清洗它。

| 交回文件 | 证明什么 |
| --- | --- |
| boot-时间戳.txt | 完整串口接收内容和启动过程 |
| session-时间戳.txt | Mac 启动参数、会话信息及可能的工具错误 |
| uname-a / os-release 文本 | 板子已登录，内核与发行版的实际输出 |
| ports-before / ports-after | 本次选中的串口来自插线后新增设备 |
| mac-arch / picocom-help | Mac 架构和工具版本、能力 |

### 出问题时停在哪里

| 现象 | 保存并带回的信息 |
| --- | --- |
| 没有新增串口节点 | 前后列表、正确接口接线照片；主板保持未上电 |
| 无法设置速率 / Settings mismatch | session 全文；可用 Ctrl-A、Ctrl-V 查看状态，再停止核验 |
| 串口已打开但无输出 | 上电顺序、接线照片、两份日志；不要连续重启试错 |
| 大量乱码 | 完整原始日志、工具参数、手册速率依据 |
| 登录失败或查询报错 | 原始提示及全部输出；不改密码和系统文件 |

本卡通过标准仍是：串口进入登录后的板子 shell，uname -a 有输出，并交回要求的完整证据。文件生成不等于硬件验收已经完成。

## 读懂这份日志，以及资料边界

**为什么先串口再网络：**串口可以覆盖内核和网络启动之前的阶段。即使系统还没有 IP 或 SSH 服务，也可能已经输出早期诊断信息。

**启动链怎样理解：**早期初始化为处理器和内存准备基本条件；U-Boot 等启动加载程序把内核带起来；Linux 内核初始化驱动并挂载根文件系统；用户空间再提供服务和 shell。把实际日志中能对应的片段标出来，无法确认的部分保留疑问。

**为什么是两份日志：**boot 文件保存 picocom 收到的原始数据；session 文件保存 Mac 终端所见内容，包括工具自身的参数和错误。前者用于保留启动证据，后者帮助排查“还没连上串口”的问题。

### 哪些已经查到，哪些仍需实测

已确认：官方硬件手册的 CH343G 和独立 USB 供电；官方旧 Wiki 的 UART 接口、1500000 默认速率和 Buildroot 登录说明；picocom 的日志、退出及 Mac 自定义速率实现。

尚需你实测：Mac 的实际串口节点、驱动能否设置 1500000、当前板子出厂固件、日志可读性和登录结果。本教程没有打开你的串口、给板子上电或修改任何板端设置。

厂商本地说明指出资料已于 2026 年 7 月迁至语雀。本次无法读取语雀《调试串口配置手册》正文，使用可访问的官方 Wiki 与本地硬件手册交叉核对；若新版手册与本教程不同，保留原文并停下核实。

本地硬件手册早期概述中存在“USB 可供板子电源”的旧句，与 §3.16 专门电路说明冲突；本教程采用 §3.16 和原理图所支持的“调试 USB 供串口芯片，主板用配套 12 V”。旧 Wiki 的 Windows 驱动名称也不作为 Mac 驱动安装依据。
