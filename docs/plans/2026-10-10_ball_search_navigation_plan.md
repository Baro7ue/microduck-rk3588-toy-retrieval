# Let MicroDuck remember the ball and keep correcting its heading

**The current scheme suits a visual-approach prototype under limited conditions, but it cannot carry full ball-search navigation.** The centre of the ball's box gives a heading error in the image, and its area gives a rough cue of distance; while the ball stays visible, this feedback is well founded. The trouble comes when it is stretched into a system that "reliably judges the distance in front of the feet and still knows where the ball is after an occlusion": that lacks metric geometry, a memory of state and recovery behaviour. Your idea of "first fix position, heading and distance" is worth keeping, but stopping visual correction after one fix lets gait error, odometry drift and ball movement keep adding up. The suggested next step is **a ball state in the local odom frame + visual correction while visible + short-term prediction + controlled re-search**, without bringing in the full ROS2/Nav2/SLAM for now. What follows is an assessment of the architecture from public source code and the existing records; no program was changed, no trial was run, and nothing is shown to be solved.

## Approaching by area has a range of use; stopping on a lost ball shows the missing navigation layer

The visual servoing literature separates IBVS, which forms its error from image features, from PBVS, which forms it from 3-D parameters estimated by vision; so "adjusting the motion while watching the ball" is not in itself the wrong direction. The current centre and area feedback follows the image-space idea, but is not yet a full IBVS controller. A feature that leaves the field of view breaks the feedback, and merely raising the time a missed detection is tolerated does not produce a ball position. ([the original visual servoing paper](https://web.mit.edu/amcp/OldFiles/drg/Chaumette_Part_I.pdf), [the author's notes on the field-of-view constraint](https://faculty.cc.gatech.edu/~seth/res.php?u=vs))

| Scheme | Reasonable use | Key limit for MicroDuck |
|---|---|---|
| Continuous feedback on image centre / area | Simple approach while the ball stays visible | Area is not the gap in front of the feet; no memory of position once detection is lost |
| Walk to the old goal after one fix | A static target, reliable own pose and a short, controlled range | Ball movement, foot slip and heading drift cannot be corrected from an old observation |
| Metric ball state + prediction + re-observation | Resuming the approach and the search after a brief miss | Needs calibration, time alignment, odometry error and validity bounds |

The suitability in the table is this project's engineering judgement, based on the classification of visual feedback above and on the definition of odom as continuous but drifting in the long run; the third fits the current goal best and is not implemented yet. ([REP-105: odom](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst#odom))

The latest record, `035720`, is a controlled stop after the ball was cut off / lost on the left, logged as `stopped_missing_ball`, with the stop confirmed and the robot left standing; it must not be retold as a fall, nor taken as navigation done. The current chain is vision on the RK3588 NPU and the policy on the CPU, with the Mac's MuJoCo providing the body and the camera: **this is not a validation on a physical robot**. The actual turning response and its timing still have to be checked separately; adding state estimation will not repair the gait's turning by itself. ([this project's latest record](</Users/ethan/Documents/RK3588 Microduck/task/evidence/G4/ball_follow_npu_20261010_035720/summary.json>))

## Mature systems remember coordinates and confidence, not the last heading command

B-Human keeps the ball's position, velocity, covariance and time of last observation; after the robot moves, it transforms the past state into the current body frame with odometry and then updates it with new vision. Bit-Bots' current public implementation transforms 3-D ball observations into odom by timestamp and keeps a position and a covariance; on a miss it raises the uncertainty, but this implementation has no ball-velocity state. What can be borrowed is "the estimate stays, its confidence drops, and behaviour decides separately"; not every implementation should be loosely called a full motion Kalman tracker. ([B-Human ball model](https://github.com/bhuman/BHumanCodeRelease/blob/d89d603f0388208cecd1c3144b6e8eb92aef4a93/Src/Representations/Modeling/BallModel.h), [ball state propagation](https://github.com/bhuman/BHumanCodeRelease/blob/d89d603f0388208cecd1c3144b6e8eb92aef4a93/Src/Modules/Modeling/BallStateEstimator/BallStateEstimator.cpp), [Bit-Bots ball filter](https://github.com/bit-bots/bitbots_main/blob/a9b62760085e77f36e541ea00eacab71d5a4775a/src/bitbots_world_model/bitbots_ball_filter/bitbots_ball_filter/ball_filter.py))

For MicroDuck the ball state needs at least a position, a reference frame, an observation time, an uncertainty and an "observed / predicted / lost" flag. The robot state keeps its own position and heading. **A visual ball observation updates the ball estimate; a ball that can move and whose world position is unknown must not be used as a static landmark to correct the robot's odom.** The current kinematic odom is itself an estimate still to be assessed, not truth; multiplying the velocity command by time is only a model prediction and cannot replace feedback of the actual motion. A local odom frame is enough to carry a short-range goal; a map is not a precondition. ([frames and control inputs in state estimation](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst))

What can be borrowed from Nav2 is likewise a goal pose with a time and a frame, a robot pose that keeps being updated, and bounded recovery. It does not do monocular ranging for us; the Following Server version checked here even forces its own collision detection off and cannot be taken as full obstacle protection. RoboCup's search durations and Nav2's timeouts and angular rates cannot be copied to a biped. ([Nav2 goal transform and control](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L345-L399), [the collision detection limit](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L61-L72))

## A 70 mm ball gives scale, but calibration and timing decide whether the position can be trusted

Under ideal fixed imaging, area falls roughly with the inverse square of distance, so it can express rough scale; cut-off, occlusion, box error and camera pose break the assumption that a fixed area means a fixed distance in front of the feet. With the ball's diameter known, `D=0.070 m`, far away, near the optical axis and with a whole outline, the depth along the optical axis can be estimated from `Z≈fD/d`; this is still not the distance from the foot to the ball's surface, and a YOLO box need not fit the true diameter. The intrinsics and distortion should be calibrated first, and the intrinsics adjusted together with any image scaling. ([OpenCV camera model](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html))

The other constraint is that the ball is on the ground: with the ground at `z=0`, the ball's centre is at `z=0.035 m`, and the undistorted ray through the centre is intersected with the plane at that height. That needs the camera's height above the ground and its orientation; the IMU gives attitude and cannot give height alone, and the forward kinematics of the head joints and the body geometry must give the camera extrinsics. When the ray is near the horizon, the intersection falls behind the camera or the ball is in the air, the on-the-ground observation should be rejected. When the diameter method and the ground method clearly disagree, the observation should be down-weighted or ruled invalid, and the geometric error checked first. ([B-Human plane projection](https://raw.githubusercontent.com/bhuman/BHumanCodeRelease/master/Src/Tools/Math/Transformation.cpp), [sensitivity to camera pose](https://docs.b-human.de/master/perception/perception-infrastructure/))

These transforms must use the head and body pose **at the moment the image was captured**, and then the robot pose at control time to get the ball's current relative position. The existing TCP images carry no capture timestamp from the source, and the arrival time of a whole frame only approximates the capture time; while the head swings, this offset becomes an error in heading and distance. Adding a frame number, a source time and a clock mapping across machines should come before any claim that filtering has solved the delay. ([the existing protocol](</Users/ethan/Documents/RK3588 Microduck/work/probe_runtime_visual_load.py>), [matching the pose at capture time](https://docs.b-human.de/master/perception/perception-infrastructure/))

## Validate observation and own motion first, then decide which actions prediction can support

Three new layers are suggested: a metric ball observation handles geometry and quality, a ball state handles memory, prediction and visual updates, and an approach / search supervisor handles aligning, slowing, stopping, re-acquiring and finishing. Own odom feeds the last two in parallel; the existing gait takes velocity targets. A 2-D tracker mainly solves target association and cannot replace a metric state. If "line following" means walking along a line on the ground, it should rest on the line's position and direction; if it means tracking a planned path, on the path and the own pose; neither can rest on the last ball position alone. ([Nav2's layering of goal updates, planning and path tracking](https://github.com/ros-navigation/docs.nav2.org/blob/76849a4062be342499889f4442838d6ecca77046/docs/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following.md))

Validation starts with static geometry offline: at different distances, head poses and edge cut-offs, compare the two ranging methods with a true reference position; simulation truth is used only for scoring. Next come static occlusion and a moving ball, checking the prediction flag, expiry and wrong re-acquisition. Then the actual displacement, heading and odom error of walking straight, turning left and right and switching between stop and go are checked independently, and only last are occlusion while moving and the stopping gap in front of the feet assessed. These are levels of later acceptance; none was carried out here, and the old closed-loop tests need not be repeated.

For now the zero-velocity protection on a lost ball can stay, while estimation continues and waits for recovery; a valid prediction is not permission to keep walking. On a timeout, an invalid pose or an uncertain identity, the approach is left; a controlled head sweep / turn-around search starts only once the robot stands firmly. The validity period and the range of actions should follow from the evidence on observation delay, drift, turning response and stopping, without presetting "may walk blind for a few seconds". ([the basis for bounded recovery](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L289-L342))

## Conclusion

The next decision point should be: can the current visual geometry and own-motion estimate support a bounded local target state? If the evidence falls short, the memory of state can still guide the re-search after a stop; if it holds, then discuss which actions are allowed during a short occlusion. That way each new ability has its own acceptance condition, and "a changed architecture" is not mistaken for "turning, ranging and navigation are now reliable".
