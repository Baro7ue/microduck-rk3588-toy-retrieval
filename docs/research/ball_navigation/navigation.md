# Target-following navigation, odometry and handling a lost target

## 1. How does Nav2's mature following interface represent the target, stopping and a lost target?

### Takeaway

Nav2 takes a "target pose" as input and keeps computing control with the robot's new pose; it does not treat a detection box as a navigation goal. That structure can be borrowed, but its lost-target wait time, turning controller and search motion cannot be taken as a verified scheme for MicroDuck. [Official dynamic object following tutorial](https://docs.nav2.org/rolling/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following/)

### Cited Findings

- **Checked on 2026-10-10. Version bounds:** the Following Server is listed in the **Kilted -> Lyrical** migration guide, and PR #5565 added `opennav_following`. This note checks Nav2 `main` at `3286119753ce1fab9d2ff411ea6d439b823fe18d` (2026-10-09), where the package version is **1.5.0**; it cannot be assumed from this that the older Humble/Jazzy have the same interface. [Migration guide, pinned version](https://github.com/ros-navigation/docs.nav2.org/blob/76849a4062be342499889f4442838d6ecca77046/docs/configuration_and_development/migration_guides/kilted/Kilted.md#following-server--kilted-to-lyrical-following-server-), [package.xml](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/package.xml)
- **The real action:** the `FollowObject` goal of `follow_object` contains only `pose_topic`, `tracked_frame` and `max_duration`. The target can come from a `PoseStamped` topic with a frame and a timestamp, or from a TF frame; detection and target localisation have to be supplied by external modules. `desired_distance` and `detection_timeout` are server parameters and cannot, following the tutorial's loose wording, be written as fields of the action goal. [FollowObject.action](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_msgs/action/FollowObject.action), [subscription and action initialisation source](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L47-L72), [dynamic object tutorial](https://docs.nav2.org/rolling/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following/)
- **Target and own motion kept apart:** topic mode transforms the detected pose by its timestamp into a fixed frame (`odom` by default); every control cycle it gets the robot's new pose and then computes the goal point that keeps the given distance. The distance here is the geometric distance from the robot's base origin to the target position; the source has no geometric definition of a "gap from the front foot to the ball's surface". [getRefinedPose / approachObject / getPoseAtDistance](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L345-L399)
- **A first miss is not an immediate stop:** topic mode caches the last detected pose and may keep using it as long as the detection timestamp is within `detection_timeout`; once the target times out it throws a detection failure, goes into a bounded number of retries, and finally publishes zero velocity and ends. The recoverable exception branch does not guarantee zero velocity first on every failure. So it cannot be described as "any miss stops it at once". [Detection freshness and failure handling source](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L289-L342), [cache and timeout check](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L496-L558)
- **Bounded search, off by default:** the current defaults are `detection_timeout=2.0s`, `max_retries=3`, `search_by_rotating=false`, `rotate_to_object_timeout=10.0s`. With search on, it tries the positive and the negative `search_angle` around the initial heading, checking for a new detection while rotating; on reaching the given distance it first zeroes velocity and waits for the target to move. These are software defaults, not safety evidence for a biped. [Parameter source](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/parameter_handler.cpp#L35-L70), [search source](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L402-L476)
- **Scope of the capability:** this version of the Following Server forces its own collision detection off at initialisation and says explicitly that it is not supported. That a following interface exists does not mean full obstacle avoidance and motion safety are in place. [Initialisation source](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L61-L72)

### Inferences

- **Structural inference for this project:** borrowing four interfaces is enough: the target pose, observation freshness, a continuously updated robot pose and bounded recovery; there is no need to move to the whole ROS2/Nav2 for one ball. With a static ball as the target, what is kept for a short time is "the ball position estimate in a local frame", with own motion updated alongside, not the last forward speed. [Structural basis](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L345-L399)
- **Inferred conservative policy for this project:** after a miss, zero velocity can be requested at once while estimation continues for a short time and waits for observations to come back; past the freshness limit, with an invalid pose or an uncertain identity, stop. Active search should be a separate state, enabled only once the robot stands firmly, has stopped moving forward and its turning response has been verified. How long to wait follows from the observation interval, latency, odometry error and stopping distance; Nav2's 2 seconds cannot be copied. [Basis of the bounds](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/parameter_handler.cpp#L35-L70)

### Gaps

- The official following tutorial does not solve, for this project, the metric distance of a ball from one camera, re-identifying the target or the stability of a biped gait, nor does it give timeouts and search angular rates fit for MicroDuck. So this note offers no new control parameters, and still less treats the official feature as validation on the board. [The tutorial explicitly leaves target detection and localisation out of scope](https://docs.nav2.org/rolling/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following/)

## 2. How does walking open-loop after one fix differ from odometry prediction plus visual correction?

### Takeaway

There is no need to choose between "control directly from every frame" and "walk blind after one sighting": the robot's pose is updated continuously, the target estimate is corrected while the target is visible, and predicted with growing uncertainty while it is not. A local demo can use `odom`; adding a map is not a precondition for this structure. [REP-105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst), [robot_localization state estimation documentation](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst)

### Cited Findings

| Frame | Official meaning and role in control |
|---|---|
| `base_link` | Fixed to the robot's body; used to express the robot's current direction relative to the target. [REP-105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst#base_link) |
| `odom` | A world-fixed local reference; the robot's pose should be continuous, but its error can grow without bound over time; suits short-range local control. [REP-105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst#odom) |
| `map` | A world reference corrected by global observations; it can jump; suits long-term global localisation. [REP-105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst#map) |

- **A map is not required:** `robot_localization` says explicitly that without a `map_frame` it can be removed and `world_frame` set to `odom_frame`. When only continuous odometry, visual odometry or an IMU are fused, `odom` is also the default. [frame parameter documentation](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst#frame)
- **Prediction and correction by observation are two steps:** the current `robot_localization` rolling-devel is `7dfb6aa97b2082185d2fac3420888ae8474bfc1a`, package version **3.10.1**. Its EKF predicts forward with a motion model and then corrects with sensor observations; on a sensor timeout it can predict only. `smooth_lagged_data` supports going back to the historical state before a delayed observation and replaying from there, provided the timestamps are right and there is enough history. [Version](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/package.xml), [estimator and sensor_timeout / smooth_lagged_data](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst)
- **Odometry memory needs a freshness limit:** REP-105 explicitly requires data that is too old or too far away to be dropped according to the odometry's accuracy; a platform with accurate redundant encoders and one with weak turning feedback cannot use the same data retention time. [REP-105 on retaining odom data](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst#transitions-between-maps)

### Inferences

- **The suggested minimum coordinate chain, a design inference:** for an observation at `t_m`, first use the body pose and the head extrinsics of that same moment to bring the ball position into the local frame: `p_ball^odom = T_odom_base(t_m) · T_base_camera(t_m) · p_ball^camera(t_m)`. At control time `t_now`, use `T_base_odom(t_now)` to get the ball's current relative position. This chain compensates the robot's translation and the head's motion; compensating only the image rotation does not maintain a full metric target state. [Basis: the official use of the target transform at observation time and the robot pose at control time](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L496-L558)
- **Two estimators should be kept apart, a design inference:** the robot estimator maintains own position, heading and velocity; the ball estimator maintains the ball's position, optionally its velocity, the time of last observation and the uncertainty. The camera-relative position of an ordinary unknown ball cannot be passed off as "the robot's absolute position" and fed into the robot's own EKF. Only a landmark at a known position, with a correct measurement model, can constrain the robot's localisation in return. [Definition of the robot state variables](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst#sensor-config), [target pose interface](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_msgs/action/FollowObject.action)
- **Open loop and prediction must not be confused, an engineering inference:** working out the distance moved by multiplying the forward command by time is a prediction from the control model; only odometry with independent motion observations and repeated correction gives feedback. Letting the estimator keep computing during a short miss does not mean letting the robot keep walking. A filter can only combine information within its model and observation assumptions; it cannot guarantee to repair wrong calibration, bias, the actual turning response or a fall. [The official bounds on the EKF model and control input](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst#use-control), [bounds on odom drift](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst#odom)
- **A constraint from this project's context, not a new verification:** the kinematic estimate `odom.position` already exists and can serve as an input still to be assessed; its drift and invalidity flags should be kept, and it cannot be taken as simulation truth. Frames, timestamps, observation quality and measurement error should be settled first, and only then whether to use a Kalman filter. This suggestion follows from the state estimation contract above; the existing odometry was not measured again in this round. [Design basis](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst)

### Gaps

- The project's limit that the current camera protocol has no exposure timestamp from the source cannot be removed automatically by "adding an EKF"; this round did not settle an acceptable clock error, odometry covariance or target distance error. The coordinate chain above requires these interfaces to be defined first. The official delay correction depends on observation times and historical states and is no evidence that the existing reception time equals exposure time. [Preconditions for handling historical data](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst#smooth-lagged-data)

## 3. Are line following, target following and ball search one module?

### Takeaway

Path tracking takes a path as input, target following takes a changing target state, and ball search decides where to look and when to give up. They can be chained, but none can replace another. [Nav2's two official dynamic following methods](https://docs.nav2.org/rolling/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following/)

### Cited Findings

- The official tutorial gives two routes: the dedicated Following Server; or, in a behaviour tree, `GoalUpdater` updates the goal, `ComputePathToPose` plans, `TruncatePath` keeps the following gap and `FollowPath` tracks the path. The second route's example replans at 1 Hz, and goal updating and path tracking are different nodes. [Tutorial source, pinned version](https://github.com/ros-navigation/docs.nav2.org/blob/76849a4062be342499889f4442838d6ecca77046/docs/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following.md)
- After reaching the desired distance the dedicated server publishes zero velocity and keeps waiting for the target to move; searching for a lost target is an optional recovery limited in angle and time. [Arrival handling](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L249-L277), [rotating search](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L402-L476)

### Inferences

- **Suggested minimum prototype:** `visual detection / range observation -> ball state estimate` in parallel with `IMU / leg motion observation -> own local odometry`; both feed `approach and search state machine -> velocity command -> the existing gait control`. Searching for a ball over a short range in the open needs no path planning, map or SLAM at first; if obstacles and given routes come later, add planning and path-tracking modules then. [Structural basis](https://docs.nav2.org/rolling/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following/), [odom mode without a map](https://github.com/cra-ros-pkg/robot_localization/blob/7dfb6aa97b2082185d2fac3420888ae8474bfc1a/doc/state_estimation_nodes.rst#frame)
- **Suggested layers for a lost target:** with no target established yet, stay stopped and search for the ball; with a target established, a short miss can wait at zero velocity while the position is predicted and the uncertainty grows; an observation that comes back must be confirmed to be the same identity; on a timeout or too much uncertainty, leave following, and only a controlled search may recover it. Head search and body rotation should each have their own stop condition; "keep predicting" must not become a reason to walk forward without limit. [Basis of bounded recovery and observation freshness](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L289-L342), [basis of the data retention limit](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst#transitions-between-maps)
- **Suggested stopping measure:** if "about 20 cm from the front foot to the ball's surface" is required, the target centre distance, the ball radius, the front foot's geometry and the stopping motion should be tied together and the arrival condition defined separately. Target state estimation, the arrival check and gait stability are verified separately; a navigation library's base-to-object distance does not automatically equal that gap at the foot. [Basis: how Nav2 constructs the distance](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp#L616-L629)

### Gaps

- This research gives structural suggestions only. It does not show that the existing gait can steadily execute the angular rates needed, nor that the existing monocular ball localisation and odometry are enough to hold a 20 cm gap. Finishing the research is no permission to widen the range of motion or to claim success on real hardware; experimental evidence is needed separately for own motion, metric position from vision, stopping and gait response. [The range the official interface and implementation support](https://github.com/ros-navigation/navigation2/blob/3286119753ce1fab9d2ff411ea6d439b823fe18d/nav2_following/opennav_following/src/following_server.cpp)
